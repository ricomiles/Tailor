- (decision) Paradigm: hexagonal (ports and adapters) at the system edge, pipes-and-filters for the six-step tailoring run inside the core. Chosen over idiomatic-layered and over hexagonal-only-around-the-core. Binds all modules. Prevents: the domain core acquiring Next.js/Drizzle/Playwright/CLI dependencies, which would make 'nothing reaches the resume without passing validation' a discipline instead of a structure, and would break the spec's promise that an API-key model impl swaps in with no other file touched.
- (decision) Rationale kept out of the spine: user weighed the single-user-local-tool objection (interfaces with exactly one implementation forever) and accepted the ceremony because the trust premise is the product.
- (decision) A tailoring run is a background job, not a streamed request. POST returns a runId immediately; the run proceeds server-side writing per-step start/end to a run_steps table; the client polls. Chosen over SSE and over SSE+persist. Prevents: a mid-run refresh orphaning the UI, and per-step durations having no persistent home (the SPEC data model has no place for them today).
- (decision) Data model gap found and closed by the above: SPEC data-model.md has no run_steps table, so the six per-step durations the SPEC demands ('real progress, never a spinner') had nowhere to live. The spine adds it. Also means a rejected run still records where the time went, matching the SPEC constraint that every run is kept as signal.
- (decision) The two overclaim checks live in exactly one pure, dependency-free domain module (no fs, no Drizzle, no Node built-ins) imported by both client and server. Client runs it for instant per-edit feedback; server re-runs the same module authoritatively before approve and before render, never trusting client-reported flag state. Prevents: two drifting implementations of the same rule, where a laxer client check lets an overclaim through the gate the product exists to hold.
- (decision) Consequence accepted: a canon projection (bullet id, text, tags, role) is served to the client so the isomorphic checks can run there. Safe because the app is single-user on localhost; the projection is read-only and never a write path into canon.
- (decision) ResumeDocument is a pure function of fully-resolved props: no hooks, no store access, no client-only APIs. AND both call sites build props through one shared props-builder (review screen from the Zustand slice, PDF route from DB rows). Prevents: the PDF route being unable to render a store-coupled component and forking it — and equally, the two sides feeding one shared component different inputs so the preview silently stops matching the PDF.
- (decision) One canon gateway module is the only code that opens resume.canon.json. Reads re-parse per operation (no cache, no invalidation class of bug). The single needs-number write path writes temp-then-rename and snapshots a timestamped backup first. Prevents: four readers each owning their own parse and shape assumptions, and an interrupted write truncating a gitignored, irreplaceable file with no version-control safety net.
- (decision) Outcome D added: 'run could not complete' — CLI missing, timeout, non-JSON, ModelOutput shape mismatch, board fetch failure, Chromium/PDF failure. Records the run as failed with the failing step, leaves the posting Discovered, and never writes rejections.log. Prevents: infrastructure noise polluting rejections.log, which the SPEC keeps deliberately as signal about the prompt — a network blip must never read as the model lying.
- (decision) ModelOutput is shape-validated (schema/zod) before any semantic validation runs. A payload that parses as JSON but does not match the ModelOutput type is Outcome D, not Outcome A. Prevents: a malformed model response being misread as fabrication.
- (decision) One error envelope shared by every route handler. Prevents: per-route error shapes and the client growing bespoke handling per endpoint.
- (decision) Zustand is the working copy during review; a debounced write persists diff_items.user_edit continuously. Server re-validates everything at approve regardless of client state. Prevents: a refresh or crash discarding a whole review session on top of a paid model call, and ambiguity over whether the store or the DB is the record.
- (decision) Idempotent bootstrap routine: creates ./data, seeds resume.canon.json only if absent (never overwrites), creates boards.json with a documented shape, applies versioned Drizzle migration files. Chosen over drizzle-kit push. Prevents: push converging the schema by dropping columns/tables that hold real posting, run, and diff history — and prevents a re-run clobbering canon.
- (decision) One domain module owns tag extraction, called by both the queue score and the fabrication modal's closest-real-experience matcher. It matches free text against the controlled vocabulary already present in canon's tags[] plus normalization/aliases, rather than open-ended keyword extraction. Resolves SPEC open question 2. Prevents: two consumers scoring the same text differently, and unexplainable scores — every match names a canon tag.
- (decision) One render-readiness gate: a single domain function returns every reason a run cannot render or be approved — unfilled needs-number placeholder in a selected bullet, TODO contact fields in basics, a selected needs-content bullet. One banner pattern in the UI. Resolves SPEC open question 3 as BLOCK on incomplete contact line. Prevents: Outcome C and contact-completeness becoming two code paths and two banners solving one class of bug twice.
- (decision) The six run steps are the literal pipeline stages: each a discrete typed filter function, executed and timed by one pipeline runner that writes start/end per stage to run_steps and short-circuits (step 6 never runs after a rejection). The six are a fixed contract, not a growable list. Prevents: reported durations diverging from the real work, which would make 'progress is real, never a spinner' false by construction.
